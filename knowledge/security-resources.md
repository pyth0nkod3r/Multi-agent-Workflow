## Article digest — the 4-phase workflow + one-shot prompt structure + 7 shortcuts (full text now captured)

Source: "The Best Claude Code Setup for Bug Bounty Hunting" by 𝙇𝙤𝙨𝙩𝙨𝙚𝙘, InfoSec Write-ups / Medium, 27 Aug 2026. **Previously paywalled (only 3 public sections captured — see git history of this doc); a FULL PDF was uploaded and extracted this run (pdftotext, 967 lines) — the entire member-only body is now on record below.**
Note: article is bug-bounty (offensive) in framing; every element is repurposed here as a DEFENSIVE checklist against our own products only (see CRITICAL flag in the Mapping section).

### Burp Suite MCP setup (agent-to-proxy bridge)
- Install "MCP" extension from the Burp BApp Store; configure **Auto-Approved HTTP Targets** (wildcard) so the agent never pauses on per-request permission prompts.
- Load the PortSwigger JAR (PortSwigger/mcp-server on GitHub).
- Connect: `claude mcp add burp --transport sse http://127.0.0.1:9876`.

### Traffic collection pipeline
1. Scope the target; filter proxy history to in-scope requests.
2. Manual crawl + Burp Engagement Tools → Discover Content.
3. Filter to **parameterized requests** (the testable surface).

### 4-phase AI workflow
1. **Understand:** list/understand captured history + build an API endpoint inventory + scan responses for sensitive data.
2. **Map attack surface:** injection candidates, numeric IDs, admin endpoints, JS files.
3. **Active testing:** SQLi, XSS, IDOR, weak creds, enumeration, rate limiting, broken access control, business logic.
4. **Report:** professional writeup with severity / evidence / remediation.

### One-shot prompt structure (6 sub-phases)
ROLE (senior hunter, evidence-first, never inflate severity) →
1. Pre-engagement intel & surface modeling
2. Attack hypotheses ranked by (impact × likelihood) ÷ effort
3. Exploitation order: business logic → IDOR → auth/session → access control → injection → OOB Collaborator → file upload
4. Chaining & impact amplification: IDOR pivots, JS-leaked API keys, kill chains, variant sweep
5. Validation gate: Repeater replay, prove impact, kill findings you can't stand behind
6. Professional report: exec summary, CVSS 3.1, evidence appendix

### 7 Burp-less shortcuts
1. Raw Burp request analysis (user-controlled inputs, IDOR/BOLA candidates, injection points).
2. JS file analysis (API endpoints, hardcoded secrets, DOM sinks, feature flags).
3. JS-from-URL fetch.
4. Multi-JS consolidated attack-surface map.
5. Single-vuln second opinion.
6. Source-code security review (auth weakness, access control, injection, session mgmt, business logic — root cause + fix + validation).
7. Report generation from evidence.

**Detail on the 4 read skills (SKILL.md fetched, main branch):**

1. **org-attack-surface** (~64 KB): legal-identity → owned-internet-footprint attribution. Org-first attribution pyramid (legal entity → LEI/registration → corporate family → domains → netblocks/ASN → live assets). Sources: GLEIF LEI API (exact-LEI BFS, downward-only), SEC EDGAR full-text + Exhibit-21 subsidiary names, OpenCorporates, Wikidata SPARQL (P856/P355/P749/P1830), reverse-WHOIS, crt.sh `?O=` CT pivot, RIR "dark netblock" recall (ARIN Whois-RWS, RIPE DB org + inverse-org), ASN via RIPEstat+BGPView union. **Hyperscaler-scope guard** (never attribute whole AWS/GCP/Azure/Cloudflare ranges to a tenant), Ownership-Tier combiner (1-prod(1-w_i), NONE→CONFIRMED), discover-only `related:` candidates never auto-scanned. §0–§11 incl. confidence levels, output format, source hygiene, "Do NOT" list.
2. **email-domain-security** (~47 KB): composite email-spoofability verdict computed from published DNS only. The core teaching: **envelope MAIL FROM (which SPF authenticates) vs header From (which only DMARC governs) — SPF `-all` alone is NOT spoof-proof**, and SPF `+all` bypasses DMARC even p=reject pct=100. RFC 7208 §4.6.4 10-lookup PermError fail-open (runnable stdlib lookup-counter script), SPF-include-takeover supply-chain vector (dead include re-registration inherits SPF-pass authority) with transient-SERVFAIL vs NXDOMAIN discipline. Fully passive: DNS TXT reads only.
3. **cloud-saas-exposure** (~44 KB): bucket discovery via observed-name mining + bounded 6-prefix × 15-suffix permutation; existence (HEAD/GET) vs public-listing confirmation; 9-tier object-key triage (DB dumps, credentials, IaC state, kubeconfig, VCS dirs, PII, logs…); dangling-CNAME bucket-takeover detection; **ownership-gated severity model** (unattributable public bucket ≠ false CRITICAL); offline AWS account-ID recovery from leaked AKIA/ASIA/AROA key (base32 decode, stdlib Python, canonical test vector); dependency-confusion confirmation (internal-signal classifier + read-only public-registry 404 + npm scope-claimability nuance); passive K8s/CI control-plane fingerprinting (kubelet 10250, etcd, Jenkins, Argo CD…). Explicit posture: discovery only, no exploitation, no credential submission.
4. **exposure-risk-quantification** (~42 KB): FAIR-aligned quantification of already-collected findings — 0–100 + A–F org risk score (Likelihood × Impact, three ownership-aware factors), **ownership + proof demotion cap** (unproven/weakly-owned findings can't inflate the number), $-loss model (IBM/Ponemon per-record cost bands, cross-source dedup, threat-factor annualization → ALE), attack-path amplification (red-team chain catalog + graph-walk engine, kill-chain honesty gate), board one-pager (hero $, letter grade, top-3 findings, top attack path, the ask). Passive analysis only.

Posture note (all 4, verified from §1 "Authorization & Legal Posture" sections): skills hard-code authorization/legal posture, confidence levels, source-hygiene/citation rules, and "Do NOT" lists before any technique content — i.e. they are defensively-disciplined even though framed for authorized recon.

## Mapping to a SECURITY phase for our projects — concrete usage

**Scope flag (binding on all units):** the Claude-BugHunter and Claude-OSINT skills are written for bug-bounty / authorized-external-recon (OFFENSIVE) use against targets. We adopt them ONLY as defensive checklists and test suites against OUR OWN products (our own repos, our own staging environments, our own email domain, our own cloud accounts). No skill or check is ever run against a third party. Both repos' own "Authorization & Legal Posture" sections encode the same boundary — keep those sections intact when adapting.

- **SEC-1 — Threat modeling + attack surface (per project, at design time):**
  - `org-attack-surface` as the *method* for mapping what is actually ours: LEI/EDGAR/crt.sh O= pivot + RIR dark-netblock recall + hyperscaler-scope guard, applied to our own org → produces a defensible owned-asset inventory (domains, netblocks, cloud footprints) before any hardening work.
  - `cloud-saas-exposure` (bucket discovery + dependency-confusion confirmation + K8s/CI fingerprinting) run against our OWN cloud accounts only: verify bucket ownership gating, decode leaked key IDs offline, check npm/PyPI namespaces we use internally.
  - OWASP Threat Dragon: one DFD per product (backend, web frontend, mobile app, LLM-serving surface, bot listeners); STRIDE + PLOT4ai categories; store model JSON in-repo (checkable like code); PLOT4ai covers our LLM surfaces.
  - `exposure-risk-quantification`: after scanning, produce the 0–100 + A–F + $-board-one-pager per product (FAIR, ownership/proof caps) so remediation is prioritized by money, not by scanner noise.
- **SEC-2 — Secure code review / SAST:**
  - Semgrep in CI: `p/owasp-top-ten` + `p/security-audit` + custom rules (e.g. no raw user-input-to-SQL, no eval/exec, no hardcoded secret patterns) → SARIF upload, fail PRs on new HIGH/CRIT; run at merge-gate alongside existing code-quality gates v4/8 (every flagged item audited as potential zero-day — existing standing QA directive).
  - `hunt-*` skills as **code-review checklists inverted to defense**: `hunt-api-misconfig` → our API review checklist (mass-assignment guards, JWT crypto, OData/spec exposure, CORS); `hunt-auth-bypass` → auth-review checklist (SAML signature checks, legacy-endpoint matrix, Duende-BFF class pitfalls); `hunt-business-logic` → review of price/amount/quantity/verification-gate handling (server-side recalculation, token single-use); `hunt-race-condition` + `hunt-brute-force` → concurrency + rate-limit review; `hunt-llm-ai` → prompt-injection/surface review for our LLM endpoints (OWASP LLM Top 10 mapping).
  - BugHunter `bug-bounty` skill's Semgrep quick-audit section is a ready-made starter invocation set.
- **SEC-3 — Dependency + secrets scanning (CI/CD, cheap to wire):**
  - Pre-commit/CI order (from zeonedge pipeline guide, search-verified pattern): **gitleaks** (full git history, `fetch-depth: 0`) → **Trivy** (deps + container image + IaC) → Semgrep SAST → **Dependabot** as the continuous lockfile backstop.
  - Trivy also scans git for secrets — acceptable redundancy with gitleaks (gitleaks = history-accurate, Trivy = broad rule set).
  - Secrets management: .env + repo-local secrets today; Vault when the OCI VM hosts multiple services (bot listeners + backend); rotate the cron ingestion key via the admin endpoint already in place.
- **SEC-4 — API / product-specific hardening (test suite):**
  - OWASP API Security Top 10 (2023) as the scoring rubric for every endpoint we ship; Mobile Top 10 for the Android app; LLM Top 10 for LLM-serving endpoints.
  - `hunt-api-misconfig` + `hunt-auth-bypass` + `hunt-business-logic` as pre-release test scripts **against our own staging**: IDOR sweep over our admin API (including `hunt-shadow-api` — undocumented/legacy endpoints), SAML/JWT chain checks, financial-flow property tests (if we ever add payments) using `hunt-business-logic`'s disclosed patterns (coupon race, negative quantity, decimal overflow, client-trusted amounts) as test cases.
  - `apk-redteam-pipeline` Stage 2–3 inverted: jadx-decompile OUR APK, run its 60-pattern secret grep + exported-component enumeration as a release gate; add to CI for every mobile build.
- **SEC-5 — Evidence + reporting (findings management):**
  - `evidence-hygiene` discipline for any internal security report: redact our own session cookies / other-user PII in PoC artifacts, sanitize HARs (the skill's jq filters), leave triager-useful metadata visible, rotate test credentials post-exercise.
  - Adopt a per-repo `SECURITY.md` (vulnerability disclosure + scan policy + "what we don't accept" list, borrow BugHunter's `triage-validation` "always-rejected list" as the defensive twin: know what we won't fix so reviewers stop re-reporting it).
  - `redteam-report-template` (Subject/Observations/Description/Impact/Recommendation/PoC structure) as our internal findings-report format.
  - `continuous-exposure-monitoring` (BugHunter sister-repo Claude-OSINT skill): baseline→re-scan→diff loop over our own surface with FP discipline; candidate for a scheduled job later.
  - `email-domain-security`: quarterly passive check of our own domains (SPF/DMARC posture; the skill's core lesson — SPF `-all` without DMARC `reject` ≠ spoof-proof — is a real gap-class to verify).

(F: repo README — see source list; QR flow: generate QR, scan with phone, session persists to disk as .keys/.preKey/.preKeyBundle files.)

- **v7.0.0 BREAKING-CHANGE NOTICE** (README top): multiple breaking changes; migration guide at whiskey.so/migrate-latest. Original repo removed by original author; WhiskeySockets is "the only official repository". (F: raw README.md)
- **CRITICAL security advisory GHSA-qvv5-jq5g-4cgg / CVE-2026-48063 (published 2026-06-10, CVSS 9.3)**: malicious `protocolMessage` (placeholderResendMessage) → fake `messages.upsert` with forged key+payload → **message spoofing + app-state-sync corruption + history-sync spoofing**. Affected: `<6.7.22` and `7.0.0-rc.1..rc11`. Patched: 6.7.22 / 7.0.0-rc12. **Direct consequence for EaseApply: an attacker can inject forged "job posting" messages into a Baileys session → our raw_ingress ETL would ingest fake postings; the patched version is mandatory.** (F: api.github.com/advisories/GHSA-qvv5-jq5g-4cgg)

(F: raw README.md, sections "Connecting Account" / "Saving & Restoring Sessions" / "Important Notes About Socket Config")
- **Group support**: `groups.update`, `group-participants.update`, `getGroupsForMe`, groupMetadata, cachedGroupMetadata pattern recommended; groups identified as `123456789-123345@g.us`. `messages.upsert` fires for group messages (loop over array recommended). (F: raw README.md index + JID section)

## 2. Anti-ban / anti-detection
### 2.1 Known ban triggers
- **Unofficial-client detection is the core trigger**: Meta's enforcement targets "unofficial" behavior — bot/heuristic signature detection, not volume alone. Official support language (quoted across 2019–2026): "Using an unauthorized application and/or unsupported device violates our Terms of Service and can result in your account being banned." (F: help.whatsapp.com support article text, as quoted via osnews.com 2019 + chakrahq.com/article/whatsapp-business-account-restricted-fix 2026)
- **Temp-ban page names "scraping" explicitly**: "If you received a 'Temporarily banned' in-app message, it could mean you're using an unofficial version of WhatsApp or harvesting information, known as scraping. ... stop engaging in scraping or your account might be permanently banned." (F: same official support article, quoted via chakrahq 2026) — **directly targets our use case**
- 2026 industry-observed spam policy (postengage.ai, May 2026, unofficial but detailed): spam = unsolicited / deceptive / repetitive / excessive / reported; block-rate zones (<0.5% green, 0.5–2% quality drop, >2% tier downgrade). **Send-side centric** — less relevant to read-only. (F: postengage.ai/blog/whatsapp-spam-policy-2026)
- Per-issue triggers observed in Baileys tracker: **OBA blue-check accounts → instant ban on first QR handshake on datacenter IP** (#2805, Sept 2026); **joining very large groups** (#1901, Oct 2025); **status/story uploads** (#2309, Jan 2026); **message volume** (#2131, Nov 2025); **re-login loops after code changes** (#2260, Jan 2026 — 24h temp bans). (F: GitHub issues listed in Sources)
### 2.2 Techniques
- **Dedicated SIM-registered number, never personal, never VoIP-registered** (VoIP registrations "sometimes flagged as suspicious"; Twilio-trick unreliable). Cheap pay-as-you-go SIM; number stays linked but unused otherwise. (F: lumadock.com/tutorials/hermes-whatsapp-baileys-gateway, 4 Sept 2026)
- **Low connection density**: 1 number = 1 bot = 1 VPS; multiplexing many accounts on one datacenter box is a documented kill-switch (at least for OBA; standard accounts "survive" datacenter IPs — per #2805 poster). (F: issue #2805; inference for non-OBA)
- **Read-only is materially lower risk than bulk send** (inference: all documented 2026 ban reports above are send-side or account-type triggers; no 2026 report of pure passive group-reading being banned — but Meta's temp-ban text literally names "scraping", so read-only is policy-violation even if not the dominant ban trigger)
- **Human-like cadence**: conservative rate limits, jittered activity, no 24/7 machine-regular bursts; warm up new numbers gradually (10 → 20 → 30, per Medium June 2026 "Rule 4"). (F: lumadock + medium.com/@shubhodey)
- **Presence hygiene**: `markOnlineOnConnect: false` (stop phone-side "online" noise); avoid fake typing/presence signaling; don't call `updatePresence` spuriously. (F: Baileys README "Receive Notifications" section — markOnlineOnConnect flag documented)
- **Session stability**: persist auth state durably (SQL/NoSQL per README); **do not repeatedly re-scan QR** — churn of linked-device fingerprints is a detection signal (inference, consistent with #2260 pattern).
- **No verified/OBA numbers for Baileys** — use unverified consumer numbers (the ban risk profile differs dramatically; #2805). (F: issue #2805)
### 2.3 Documented 2026 ban events
- **Oct 2025 wave** (pre-2026 but ongoing into it): Baileys #1869 "High number of bans" — 5 bots banned in one week incl. two 3-year-old stable bots; even non-bot personal numbers got temp-banned; closed as stale Dec 2025 (unresolved). (F: issue #1869)
- **2026 steady-state ban stream**: #2309 (Jan, perm ban on status upload), #2260 (Jan, 24h temp bans), #2699 (Jul, restored-then-degraded account), #2805 (Sept, OBA instant ban, open). Meta enforcement volume: ~5.4M Indian accounts banned July 2026 (India IT Rules filing); Medium (June 2026) cites "8M/month globally" from the March 2026 transparency report — **global figure not independently verified** (India monthly filings verified via medianama 4 Sept 2026). (F: issues + medianama + medium)
- **1-in-5 unofficial-API accounts banned within a year** (industry estimate from Medium June 2026 — treat as anecdote, not a measurement).
### 2.4 Safest configuration for our use case
1. Unverified consumer number on a real SIM (not VoIP, not personal, not OBA)
2. Baileys 7.0.0-rc14 (or 6.7.24) on Node ≥20, **one number per VPS**, datacenter IP acceptable for consumer numbers but avoid high connection density
3. Strictly read-only: subscribe `messages.upsert` for target groups only; **never** call `sendMessage`, no presence updates, `markOnlineOnConnect: false`, no status uploads, no group-join churn
4. Target groups: prefer medium-sized groups (large-group joins are a documented trigger, #1901); cap number of monitored groups per number
5. Jittered activity, realistic online windows; persist auth state to DB; never re-scan QR unless the session dies
6. Isolate: separate HidenCloud service + separate credentials; a banned number must NOT take down the platform
(Bullets 5–6: inference from the documented triggers; bullets 1–4: F)


## 3. Security
### 3.1 Session storage & leak impact
- Baileys auth state = **creds (Signal identity keys, registration) + rolling message key material (preKeys, sessions)**; `useMultiFileAuthState(dir)` writes it to a folder (`auth_info_baileys` + `.keys.json` etc. per message). README: "For production grade system" store auth state in **SQL/NoSQL**, and `authState.keys` MUST be persisted on every `creds.update` or messages stop flowing. (F: Baileys README "Saving & Restoring Sessions")
- **Leak impact**: a stolen session let an attacker act AS the linked device — read incoming messages for that number and decrypt session-scoped history. E2EE means Meta can't read it, but **the session holder can**. This is why 3rd-party "WhatsApp recovery" services exist (F: Baileys session model; inference on leak consequences, standard for MD protocol).
- **CVE-2026-48063 (GHSA-qvv5-jq5g-4cgg)** compounds this: even a *valid* session can be fed forged `messages.upsert`/history-sync payloads (message spoofing + app-state corruption) by any group participant with the right crafted payload. **Mitigation for EaseApply: pin a patched version (≥6.7.22 / ≥7.0.0-rc12) AND treat bot-ingested content as untrusted input at the ETL** (we already wrap LLM inputs as untrusted — extend the same discipline to raw_ingress rows from WhatsApp; dedupe by WA message id). (F: advisory; inference on ETL treatment)
### 3.2 Data access / SaaS privacy
- The linked number sees **everything it's in**: all private chats, group history (up to `syncFullHistory`), contacts, media — even if we only *want* group text. A bot service that stores or logs more than job-posting text = a privacy liability. Default: no chat store (Baileys has no built-in persistence), filter-and-forward only, store raw messages at rest encrypted and drop on a retention schedule. (F: README store section + our platform privacy posture — inference)
- Pro-gated SaaS angle: the WhatsApp number belongs to **EaseApply (our own listener account), not to customers** — customers get ingested postings on the shared board; they never hand us their WhatsApp. That keeps it out of customer-data (GDPR-style) territory; residual risk = the number's own history if we ever use a personal/old number. Use a fresh dedicated SIM. (inference, design decision)
### 3.3 Isolation from the main platform
- **Separate long-running service** on HidenCloud (Node 20+, systemd/pm2), own codebase, own env; **no shared DB credentials** — the bot writes to EaseApply via the same scoped-API-key + HTTPS ingress path as the cron scrapers (existing `eask_` key pattern + a new `wa` key), i.e. platform swappable later. (F: EaseApply cron/ingest architecture, memory 18; inference)
- Secrets: bot's auth state never in git; encrypt at rest (HidenCloud disk) or put in a Postgres table owned by the bot service; FastAPI backend never holds WhatsApp credentials. (inference)

## 4. Architecture for our use case
### 4.1 Read-only group monitor on a VPS
- **Baileys over wwjs** for this workload: no Chromium (~500MB RAM saved, HidenCloud free tier is small), active RC cadence, pairing-code support (no QR needed after first link — good for a headless VPS), `messages.upsert` gives group text natively. wwjs is a fine fallback (simpler event API, 1.34.7, slower cadence, Node ≥18) but the puppeteer dependency is a liability on a cheap VPS. (F: §1.1/§1.2 facts; recommendation = inference)
- Service shape: long-lived Node process; on `messages.upsert` filter `key.remoteJid` endsWith `@g.us` ∈ monitored-set; extract text (incl. forwarded/link-preview); dedupe by `key.id`; queue; POST to backend; reconnect loop on `connection.update` close unless `loggedOut` (then alert for re-pair). Persist authState keys on every `creds.update`. (F: Baileys README event model; design = inference)
### 4.2 Job-signal filtering
- Two-layer: (1) cheap pre-filter — group allowlist + text contains apply-signal regexes (`apply`, `application`, `closing date`, `deadline`, `vacancy`, `position`, `job`, `salary`, `CTA URLs`) and/or contains ≥1 URL; (2) exact dedupe on WA message id + URL canonicalization (same ETL choke point as board scrapers, deterministic `job-` + sha256(url)[:12] id pattern from the cron-ingest fix). Store raw message + extraction candidate; LLM extraction (existing generate_json seam) optional for unstructured postings. (inference, built on EaseApply ETL facts: memory 18)
### 4.3 Persistence to remote API
- **POST to our FastAPI ingress (NOT direct Neon writes)**: keeps the Python/psycopg layer authoritative (the 3 psycopg3/WriteThrough gotchas from 24 Sept already live in the Python side), preserves platform-swappability, and gives one dedup/E choke point. Add `/v1/ingress/wa` mirroring the cron `ingest-all` contract (source=`wa`, same `raw_ingress` → board pipeline). HMAC-signed or scoped-key auth; batch 5–20 messages per POST to avoid per-message WAN round-trips (the 502-at-97s lesson: keep ingest work off the proxy window or it blows Render's ~100s limit). (F: EaseApply cron fixes, memory 18; design = inference)
### 4.4 Node.js vs Python/uv stack
- Baileys = TypeScript/Node, **no maintained Python MD-protocol library exists** (inference — the two dominant libraries are both Node; wppconnect is also Node). So: Node 22 LTS runtime on the VPS for the listener ONLY; Python/uv stack untouched; the two meet at HTTPS (bot → FastAPI). uv stays the Python tooling policy; Node is just another runtime on the box. Coexistence is trivial (systemd units / pm2). (F: registry + repo facts; "no Python equivalent" = inference, medium confidence)

## 5. Legal / ToS
### 5.1 ToS language
- **Unofficial apps/clients**: "Using an unauthorized application and/or unsupported device violates our Terms of Service and can result in your account being banned." (official support-article text, quoted via osnews 2019 & chakrahq 2026). Baileys' own README disclaimers the same: maintainers "do not condone" ToS-violating use, discourage "bulk or automated messaging usage". (F)
- **Automation**: "Bots, scripts, or grey-market tools that automate the consumer app violate the ToS. The official WhatsApp Business API is the only sanctioned way to automate." (getkanal.com, 11 Sept 2026 — secondary). Official support articles similarly tie temp bans to "automated or bulk messaging" and **scraping**. (F, secondary)
- **Scraping named explicitly** in the temp-ban support article (quoted 2026 via chakrahq) — our "read groups and harvest postings" pattern maps onto this language. (F, secondary quote of official)
- **New 2026 policy context (official API side)**: Meta's "AI providers" ToS section effective **15 Jan 2026** bans general-purpose AI assistants on the official Business API (OpenAI/Perplexity/Microsoft bots killed; EU/IT/BR antitrust probes opened) — Meta is tightening, not loosening, who may automate on-platform. (F: techcrunch.com 18 Oct 2025, update 15 Jan 2026)
- **Jan 2026**: Meta also formally restricted open-ended "assistant" bots on the Business Platform; only structured (orders/FAQ/lead-capture) automation allowed. (F: sporesec.com 6 Jul 2026, consistent with TechCrunch)
- **No "fair use" safe harbor**: the Groups API (official) exists but is invite-only/8-member — it does NOT create a right to read arbitrary public groups. Reading a group = the number you link (our SIM) is a participant; ban consequences fall on that number, not on Meta. (inference)
### 5.2 Risk assessment for hosted SaaS
- **Direct legal risk to EaseApply is LOW-MEDIUM**: WhatsApp's enforcement is account-level (ban the number), not entity-level (sue the SaaS); no 2026 example found of Meta litigating a read-only group scraper (inference — absence of evidence). ToS violation is real → contractual/ToS breach by the **number owner (us)**; the main operational risk is **churn**: numbers get temp/perm-banned (documented: 24h temp bans, #2805 OBA instant bans, 2026 steady stream), so budget for **a pool of cheap SIM numbers + re-provisioning playbook** and treat the WhatsApp source as a lossy, eventually-degraded feed like any scraper.
- **Consumer risk**: our SIM number is disposable — never a personal/corporate-identity number; a perm ban just costs the SIM. (inference, design)
- **Data risk**: ingested WhatsApp content is UGC redistributed on our board — same copyright/privacy exposure as board scrapers already have (phone numbers in postings = personal data → strip/limit before publishing; dedupe + provenance already in the LLM pipeline). (inference)
- **Commercial optics**: it is grey-market. Documenting the position: "we monitor public groups where job postings are publicly shared; read-only; user consent is the posters' public sharing" — defensible but not ToS-compliant; keep the source toggle-able per market (per-platform kill-switch in the tier system) so it can be switched off without rework. (inference, design recommendation)
- **Decision frame**: ship it on a **dedicated disposable number** behind Pro-gating, with explicit number-replacement procedure + ETL untrusted-input handling; revisit official Groups API only if Meta ever opens read access to public groups (no signal as of Sept 2026). (inference)

## Result
Research complete. All 5 areas covered from live sources (registry.npmjs.org, api.github.com, raw.githubusercontent.com, developers.facebook.com, TechCrunch, Baileys issue tracker, 2026 industry posts). Key verdicts: (1) Baileys (7.0.0-rc14, active as of today) is the best fit; wwjs is a heavier fallback; **official Cloud/Groups API cannot read public groups** (invite-only, 8-member cap) — so unofficial is the only path. (2) Ban risk is real and ongoing in 2026 (temp 24h, perm, OBA-instant); safest config = disposable SIM number, read-only, low density, jittered. (3) Security: pin patched Baileys (CVE-2026-48063 spoofing), treat ingested content untrusted, no chat-store, isolate via dedicated service + scoped API key. (4) Architecture: Node 22 listener service on HidenCloud → POST batches to FastAPI `/v1/ingress/wa` (existing cron/ingest pattern), Python/uv stack untouched. (5) ToS: scraping + unofficial automation are named ToS violations; enforcement is per-number, so operational risk (number churn) >> legal risk; run on disposable SIMs with re-provisioning playbook.
